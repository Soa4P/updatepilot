# UpdatePilot 审查 bot 设计：PR 审查 × 代码库巡检

本档回答"为什么是现在这套形态"。三个参照产品定义了这类 bot 的能力面；本文记录
每个参照我们吸收什么、明确不吸收什么，以及不变的三条自持底线。

## 参照 → 设计决策

| 参照 | 能力 | 吸收 | 明确不吸收 | 原因 |
|---|---|---|---|---|
| **Codecov** | PR 覆盖率差值评论 + SaaS 覆盖率面板 | **覆盖标注**：审查评论里附变更行的未覆盖情况 | SaaS 上传 coverage 报告；从第三方拉 uploader 脚本执行 | coverage 报告携带代码库形状，出站给第三方与本仓 egress 纪律冲突；2021 bash uploader 投毒事件是该模式的风险实锤。数据不出仓：CI 自己产 `coverage.json`，bot 只读解析 |
| **Sourcery** | AI 行级内联评论 | **内联评论**：findings 里 location 为纯行号且落在变更行内的，作为 GitHub review 内联评论发出（≤10 条） | 每个 PR 无差别 AI 评论；diff 出站给第三方模型 | 与自建审查引擎完全重叠且我们更强（完整文件上下文 + 覆盖面表 + 确定性降级）；锚点不可靠的 findings（函数名/描述性 location）硬锚到行是伪精确 |
| **Dosu** | 仓库巡检 + issue 自动回答 + 仓库知识问答 | **有界巡检（audit 模式）**：定期扫代码库，发现写入带标签的 issue，与上一份签名去重 | issue 自动回帖；无限预算全库扫描；改状态/打标自动处置 | AI 自动回帖与"回复/合并决定在人"冲突；全库无界扫描是 open wallet；巡检产出是**草稿**，处置权在人 |

## 不变的三条自持底线

1. **代码不出门**：唯一出站是我们自己配的模型端点（https + 公网地址校验 + 禁重
   向）；仓库内容只作为提示词文本进入该端点。不装第三方 SaaS reviewer/coverage。
2. **裁决在人**：bot 产出 verdict/发现/草稿，永不 approve、永不 merge、永不自动
   处置 issue。标签与评论是给人的信号，不是给人代劳的决定。
3. **fail closed + 有界**：模型故障 → needs_review；预算（调用数/字节数/内联条数）
   超限 → 显式降级并说明，不静默截断。

## v1.2.0 新能力

1. **`mode: review` 内联评论升级**：findings 的 location 解析出整数行号且该行在
   PR diff 的 b 侧变更行集合内 → 作为 review 内联评论发出（上限 10 条，多的留在
   汇总评论）。锚点不可靠的照旧进汇总——伪精确比不精确更糟。
2. **`mode: audit` 仓库巡检**：定时触发，扫描代码库（安全关键路径优先、生成物/
   二进制跳过、≤20 组×4 文件预算），产出带 `updatepilot:audit` 标签的 issue；
   与上一份审计 issue 的发现做签名去重（file + why 归一化前 80 字符），只报新增，
   上一份的照旧挂着。
3. **coverage.json 标注**：审查评论里新增覆盖面小节——变更文件里未覆盖的行数与
   占比（读工作区已有的 `coverage.json`，bot 不跑测试）。文件不存在 → 小节不出现。

## 明确不做（本档排除项）

- issue 自动回答（知识问答）——需要把 issue 流量喂给模型且自动发帖，两线都踩
  自持底线；若 issue 量大再评估"草稿模式"。
- 与第三方 SaaS 的任何集成（codecov.io / sourcery.ai / dosu 云端）——出站纪律。
- 覆盖率门槛 gating（新增行覆盖 <X% 则 block）——覆盖率是信号不是裁决，与
  "AI verdict 不构成批准"同一条纪律。
